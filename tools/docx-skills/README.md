# docx 场景技能（按场景拆分）

把「生成 Word 文档」按**使用场景**拆成多个技能，而不是堆一个巨型技能。
每个技能**自包含**，可直接作为平台的 `dotnet` 技能 `Body` 导入。

## 为什么按场景拆

本平台技能的两个硬约束（见下方「平台约束」）：

1. 技能 `Body` 是**单个编译单元**，不能 include 共享源码，`#r` 也只认 NuGet 包；
2. 执行超时：自建技能 **10 秒**、内置技能 60 秒，`Body` 越大编译越慢。

所以一个「什么都能干」的巨型技能会同时撞上可维护性与超时两堵墙。
按场景拆分后，每个技能只带该场景需要的排版参数，源码更短、编译更快、语义更清晰
（而且模型据 `Description` 选技能时也更准）。

## 产出的技能

| 文件 | 场景 | 版式要点 |
|---|---|---|
| `out/docx_gongwen.cs` | **公文**（通知/通报/请示/批复/报告） | 参照 GB/T 9704：22pt 方正小标宋大标题、三号仿宋正文、黑体层次标题、固定行距 28pt、A4 公文页边距、页脚页码 |
| `out/docx_notice.cs` | **通知 / 公告 / 说明**（简洁单页优先） | 微软雅黑标题+正文、不缩进、行距紧凑、**无页码** |
| `out/docx_report.cs` | **工作报告 / 总结 / 方案** | 黑体标题 + 宋体正文、首行缩进 2 字符、行距 20pt、支持数据表格、页脚页码 |

三者共用同一套内容块语法：

```json
{
  "title": "标题", "subtitle": "副标题(可选)", "author": "单位(可选)",
  "date": "日期(可选)", "outputPath": "D:\\out\\x.docx(可选)",
  "sections": [
    { "toc": { "depth": 2, "title": "目 录" } },
    { "heading": "一、小节", "level": 1 },
    { "paragraph": "正文段落" },
    { "numbered": ["其一", "其二"] },
    { "bullets": ["要点一"] },
    { "quote": "引用/强调文字" },
    { "table": { "headers": ["列1","列2"], "rows": [["a","b"]] } },
    { "image": { "path": "D:\\img\\pic.png", "widthCm": 10, "caption": "图 1", "alt": "替代文本" } },
    { "chart": { "type": "bar", "title": "季度处理量", "yLabel": "件",
                 "categories": ["一季度","二季度","三季度"],
                 "series": [ { "name": "工单", "values": [120,200,150] } ],
                 "caption": "图 2 季度处理量" } },
    { "pageBreak": true }
  ]
}
```

返回：`{"ok":true,"scene":"gongwen","path":"...docx","blocks":N,"message":"..."}`

### 目录（toc）

用 **Word 复杂域** 生成，依赖标题样式的 `outlineLvl`（已就位）。

- `depth`：收录到几级标题（1-3，默认 3）
- `title`：可选，目录页自己的标题
- 自动在目录后插入分页符

> ⚠️ **打开文档时 Word 可能提示“更新目录域”**（或显示占位提示文字）—— 点“是”即生成，
> 手动刷新按 `Ctrl+A` → `F9`。这是域机制的正常行为，不是文档损坏。

### 图表（chart）

支持 **柱状图 / 折线图 / 饼图**，用 ImageSharp 渲成 PNG 后按图片嵌入。

```json
{ "chart": { "type": "bar",            // bar（默认）| line | pie
  "title": "季度处理量",                // 图内标题（可选）
  "yLabel": "件",                       // Y 轴单位（可选，饼图不用）
  "categories": ["一季度","二季度"],    // X 轴类别（可选，缺省用 1,2,3…）
  "series": [ { "name": "工单", "values": [120,200] } ],
  "caption": "图 1 季度处理量",         // 图题（可选，显示在图下方）
  "widthCm": 13,                       // 图片宽度（可选，默认 14）
  "pixelWidth": 900, "pixelHeight": 480 // 渲染分辨率（可选）
} }
```

- **柱状图**：可多系列（并列柱 + 自动图例）；**折线图**：可多系列（带数据点、自动含负值区间）；
  **饼图**：只取第一个系列，图例自动附百分比。
- 也接受简化写法：不写 `series`，直接在顶层给 `values`。
- 中文标签用系统字体渲染（自动尝试 微软雅黑 → 黑体 → 宋体 → Arial → DejaVu Sans）。
- **内容太多不越界**（长标题 / 多系列 / 多分类 / 大数值都不该画出画布）：
  - 标题按可用宽度先缩字号（不低于 16）再裁剪；Y 轴刻度文案先量宽，据此定左边距（钳在 66–170px）并**右对齐**到轴线左侧（原先写死 `x=6`，数值一大就压进绘图区）；
  - 图例按宽度**换行**（最多 3 行），每项按宽裁剪，放不下的补“…等 N 项”；**占用的行数提前计入顶部留白**，否则图例会压进绘图区（原先一行横向累加 x，系列一多就冲出右边）；
  - 分类标签按**槽宽**裁剪（不再按字符数），分类过密时**隔位显示**（`stride = ceil(52/slot)`），绘制起点用 `ClampX` 夹在绘图区内（原先居中不夹取，标签会叠成一团并越出左右边界）；
  - 饼图图例每项按可用宽度裁剪、按可用高度限制行数，放不下的同样补“…等 N 项”（原先 `ly += 24` 无上限，分类一多就画出画布底部）。
  - 已知边界：刻度数值大到 20+ 位数时左边距封顶 170px，刻度文案仍可能压进绘图区（常规数量级不会碰到）。

> **为什么不做成原生 Word 图表？** 原生图表要给包内加 `ChartPart`（DrawingML 图表 schema 极严），
> 一处不合规 Word 就会报“不可读内容”。渲成图片则零风险、且在任何 Word 版本都能显示；
> 代价是**数据不可在 Word 里再编辑**。若需可交互图表，需平台支持后另行实现。

### 图片（image）

两种给图方式，二选一：

```json
{ "image": { "path": "/app/docs/a.png", "widthCm": 14, "caption": "图 1" } }
{ "image": { "imageQuery": "城市天际线 黄昏 楼群剪影", "caption": "图 1" } }
```

- `path`：服务器上的图片绝对/相对路径
- `imageQuery`：**按关键词从平台「图库」语义检索自动配图**（用户自己上传的图片，不依赖外网）
- `widthCm`：图片宽度（厘米，默认 14，范围 1–24）；也可用 `widthPercent`（相对正文宽度 %）
- `caption` / `alt`：可选，图题 / 替代文本（`alt` 写入 `docPr descr`，利于可访问性）
- 支持格式：**png / jpg / jpeg / gif / bmp / tiff**；其它能解码的（如 WebP —— 图库允许上传）
  会**按文件头判定后用 ImageSharp 重编成 PNG**（以文件头而不是扩展名为准：库里的图可能改过名），不把稿子带坏
- 像素尺寸从文件头解析（PNG/GIF/BMP/JPEG）以保证比例正确；解析不到时按 4:3 估算
- **图会被等比缩到正文区内**：既不宽过正文宽，也不高过正文高。上限由**当前页面的实际尺寸与页边距**
  算出（不写死 15.9cm）——实测踩到：原先只把 `widthCm` 卡在 ≤24cm，而 A4 正文宽约 15.9cm，
  传 20/24 就会画到页边距外（实测 24cm = 8640000 EMU vs 正文宽 5731510 EMU）。
  回归：`DocxImageFitTests.OversizedImage_IsScaledIntoTheTextArea`。

### 图库配图（`imageQuery`）是怎么接上的

Word 技能**只走图库**（没有 Wikimedia 回落 —— 要真照片请用 PPT 技能）：

1. 平台在调用文档技能前，按**触发者本人可读的图库**（岗位**绑定了就只用绑定的**）登记一个「检索范围句柄」，
   把 `imageScopeId` 注入技能入参；聊天（单聊/知聚/编排）、技能库「试运行」、桌面宿主直跑三条路径都注入；
2. 技能带句柄回环调 `POST /ag-ui/images/search`（进程内自令牌 `AGUI_SELF_TOKEN`，启动时注入），
   拿回**服务器本地路径**；
3. 技能直接嵌入该文件。

技能**只带句柄、不自报图库 ID**：入参是模型生成的，若能自报 ID 就能越权读别人的图。
该端点也只对自令牌返回路径（登录用户只拿元数据与 `/raw` 下载地址）。

**取不到图不失败**：无图库 / 库内无匹配 / 没有回调地址 → **跳过这张图**，并在返回的 `warnings` 里说清原因
（回归：`ImageQueryResolveTests`，用假平台端点把整条回环链路真跑一遍）。

### 选哪张图：显式门槛 + 上下文候选（与 PPT 同口径）

模型**看不到图库里有什么**，只会按主题写 `imageQuery`（“员工 颁奖 舞台”）。所以配图不是“拿关键词查一次就完事”：

| 步骤 | 说明 |
|---|---|
| ① 门槛 | 请求里**显式带 `minScore: 0.6`**。不传时平台按 **0.25** 兜底，而实测无意义关键词能到 0.44~0.55 —— 等于不筛，会把不相干的照片嵌进稿子。注：**图库可以有自己的检索严格度**（库设了就以库为准，可更松/更紧；见图库管理里的 `⚙️`）|
| ② 关键词检索 | 先用模型给的 `imageQuery` 查一次 |
| ③ 上下文候选 | 若这次命中**不够确定**（分数 < 0.78）或没命中，再依次用：**图片自己的 caption / alt** → **最近一个标题** → **前面最近的文字块**，每次取高分者；一旦某个候选 ≥ 0.78 就停（最多再查 3 次） |
| ④ 回显 | 返回 JSON 多了 `images[{query,fileName,score}]`：**哪条检索词胜出、用的哪张图、多少分**，配错了能自己查 |

- 为何要**分开**当候选而不是拼成一长串：实测把“caption + 标题 + 正文”拼成一句去查，关键的那个名字被旁边的词稀释 —— 人名直查 **0.88**，拼串只有 **0.63**；标题单独查 **0.62** 反而能用。
- 为何标题排前面：人名 / 产品名往往就写在标题里（典型：“高效习惯优秀进步奖 · 刘佳俊”）；图库描述恰好就是这些名字。
- 二次尝试都是**本机回环检索**，不联网；结果按查询串缓存，拆页与重复引用不会重复查。
- 两次都没配上：`warnings` 里**两条原因都写出来**（关键词 + 上下文），不要让人以为是没试。
- 回归：`Docx_ImageQuery_LowScoreHit_LosesToContextText`（按嵌入字节证明用的是高分那张）、
  `Docx_ImageQuery_ConfidentHit_SkipsContextRetry`（够确定就不多查）、`Pdf_ImageQuery_LowScoreHit_LosesToContextText`。
- 实测（真实图库 + 真实模型）：正文写“· 刘佳俊”、关键词“员工 颁奖 舞台” → 最终嵌入的**就是 `1刘佳俊.png`**（字节相同）。

**错误处理**：文件不存在 → `图片文件不存在：<路径>`；字节连 ImageSharp 都解不开（不是图片）→ 报错并带原因。
两者都返回 `"ok":false` + 可读原因，模型可据此改用其它路径或告知用户。
`path` 是显式给的，所以“给了却不存”算配置错误（报错比静默跳过好）；
而 `imageQuery` 是“去图库碰运气”，取不到只跳过该图 + 记 `warnings`。

> **为什么 Word 侧不做「正文缩字号」**：Word 是**流式排版**——段落自然分页、表格行自动长高，
> 不存在“撑出页面”这回事，给它缩字号只会让正文无谓变小。PPT 才需要，因为它的文本框是固定高度。
> 回归：`DocxImageFitTests.HugeBodyText_IsNotClipped`（300 条要点一字不少）。

### 文件命名与落盘

**不传 `outputPath` 时**，文件名取**标题**（保留中文），落到默认输出目录：

| 顺序 | 目录 | 说明 |
|---|---|---|
| 1 | `$AGUI_DOCX_OUT` | 环境变量指定的目录 |
| 2 | `<用户主目录>/agui-docx` | 环境变量未设时的默认 |
| 3 | `<临时目录>/agui-docx` | 前两者不可用时 |

> ⚠️ 容器里**必须设 `AGUI_DOCX_OUT`**，否则落到容器的临时目录（重建即丢）。
> docker-compose 已默认设为 `/app/docs`，对应 `agui-docs` 命名卷（跨重建保留）。

- 文件名只剔除**文件系统非法字符**（`/ \ : * ? " < > |`）与控制字符，**中文原样保留**。
- **同名不覆盖**：自动追加 `_2` `_3`…
- 示例：标题「关于开展平台试运行工作的通知」→ `关于开展平台试运行工作的通知.docx`

**取文件**（任选其一）：

```bash
# 单个文件
docker cp agui-group-chat-web:/app/docs/关于开展平台试运行工作的通知.docx .

# 整个卷导出到当前目录的 out/
docker run --rm -v agui-group-chat_agui-docs:/d -v "$PWD/out:/out" alpine cp -r /d/. /out/
```

> ✅ **生成的文件会随消息一起出现在前端，可直接点击下载**（已实现，见下节）。
> 上面的 `docker cp` 仅作为运维取件手段保留。

### 下载到前端（已打通）

技能执行链没有 `AttachmentStore`（不把存储耦合进技能沙箱），所以走的是**产物回档**：

1. 技能返回体里带显式标记（`produce_file`）：
   ```json
   {"ok":true,"path":"/app/docs/报告.docx","produce_file":{"path":"/app/docs/报告.docx","name":"报告.docx","bytes":2640}}
   ```
2. 网关 `AgentGateway.AttachSkillProducedFilesAsync` 扫描该标记 → 读文件 → 白名单 / 尺寸校验
   → `AttachmentStore.Save()` 得到 `att_xxx` → 挂到当前消息（`TEXT_MESSAGE_ATTACHMENTS`）。
3. 前端渲染下载卡片，走 `GET /ag-ui/files/{attachmentId}/{fileName}`。

**两个关键坑（都已修，改这块务必留意）**：

- **必须看工具的原始返回，不能只看正文**：模型经常把技能返回的 JSON 改写成自然语言
  （“已生成文档，位置 /tmp/x.docx”），标记就此丢失 —— 表现为“技能确实生成了文件，用户却看不到下载入口”。
  因此网关用 `ToolResultCollector` 单独收集 `FunctionResultContent`（权威、未经模型改写）作为主来源。
- **两种引号转义都要认**：工具返回经 `JsonSerializer.Serialize` 后引号会写成 `\u0022`（不是 `\"`），
  `ExtractProduceFileObjects` 必须把两种形式都还原，否则花括号配对成功但 JSON 解析失败，标记同样丢掉。

**安全闸**：入库前校验扩展名白名单（`AttachmentStore.IsAllowedUploadExtension`）。
技能（尤其 LLM 生成的）可能写出 `.html`/`.svg` 等可内联渲染文件，直接入库会成为存储型 XSS 载体。

## 自动编排（一键组织编排 / 组织架构构建师）

这三个技能能被**自动编排复用**：编排器知道技能库里有哪些现成技能，会优先引用而不是另造。

**规则（库内优先，但有边界）**：

| 方案里的技能条目 | 行为 |
|---|---|
| 引用库内技能且**正文为空** | 视为「纯引用」→ 直接挂载库内那份，不重建 |
| 与库内同名但**写了正文** | 视为「要造新技能」→ 按既有语义**改名避重**（`docx_report` → `docx_report_2`），**不覆盖**库内那份 |
| 既不在库内、方案里也没定义 | 仍报「未定义技能」（不静默落库） |

> 为什么用“正文是否为空”区分：模型被要求**直接引用**时只会列 id/名称/描述（无正文），
> 而真要造技能时必然要写正文 —— 这是可拿到的、最可靠的意图信号。若不加区分就一律“库内优先”，
> 会破坏既有的“重名改名不覆盖”语义（已有回归测试钉住）。

**覆盖到的入口**：

- 网页「一键组织编排」（`POST /ag-ui/agents/orchestrate` 及流式版）
- 内置「组织架构构建师」的 `org_plan_draft` / `org_design` 出稿

两个入口都已在提示词中列出现成技能清单（最多 40 条，防提示词过长）。

> ⚠️ 编排出的岗位能否真正调用 `docx_*`，还取决于该技能的**执行前提**：
> dotnet 技能一律需人工审批；容器部署需已装字体（见下方「运行时依赖」）。

## 开箱即用（内置技能）

这三个技能已作为**内置技能随平台分发**：新部署启动即具备，无需手工导入。

- 实现：正文以**嵌入资源**随 `AguiGroupChat.Agents` 分发，启动时由 `BuiltinDocxSkills` 播种。
- **可关闭**：`Agents:BuiltinDocxSkills=false`（默认 true）。
- **升级会刷新**：内置技能的正文随平台发布，升级后已部署实例会用**新正文**刷新（否则修好的实现上不去）。
  判断“未改过”的依据：带 `BuiltinVersion` 标记，或（字段上线前的旧数据）`OwnerId` 为 null。
- **用户改动优先**：你经界面编辑过的内置技能（`OwnerId` 非空、标记置空）不会被升级覆盖。
- **删除后会回来**：界面删除后重启会重新播种（属于“开箱即用”能力的语义）。
  要永久关闭请用上面的配置，而不是删除。

因此 `import.mjs` 现在主要用于：**把改过的技能重新推上去**、或导入到不开内置的部署。

## 导入到技能库

生成物可直接导入平台，无需手工粘贴：

```bash
node tools/docx-skills/import.mjs --base http://localhost:5200 --user <管理员> --pass <密码>
# 或使用令牌：
node tools/docx-skills/import.mjs --base http://localhost:5200 --token <令牌>
```

可选参数：

| 参数 | 说明 |
|---|---|
| `--only docx_gongwen,docx_report` | 只导入部分技能 |
| `--dry-run` | 只打印将要导入的内容，不调用接口 |
| `--force` | 已存在则改为更新（PUT），否则跳过 |

导入后：**AI 角色管理 → 🎯 技能库** 可见；挂载到数字员工的「技能与知识」里即可使用。

> ⚠️ `dotnet` 技能**仅系统管理员可创建**（平台安全策略），且**每次执行都需人工审批**。
> 若导入报 403，请换管理员账号或 `--token`。

### 一个重要区别：种子技能 vs 导入技能

平台有两类技能：

- **种子技能**：写在 `appsettings.json` 的 `Agents:Skills` 里，**常驻不可删**。
- **运行时技能**：经 API 导入，随技能库持久化，**可在界面删除**。

本工具走**运行时导入**（第二类）。原因：这三个技能正文各约 45KB，
塞进 appsettings 需整段 JSON 转义，不可维护；且会在每次恢复时与快照叠加。

## 文件说明

```
tools/docx-skills/
├── generate.mjs     ← 共享内核 + 场景配置（唯一需要维护的地方）
├── sync-builtin.mjs ← 同步到平台内置副本（嵌入资源）
├── import.mjs       ← 导入脚本（把 out/ 下的技能推进技能库）

    ├── docx_gongwen.cs
    ├── docx_notice.cs

```

## 生成方式

**不要直接手改 `out/` 下的文件** —— 它们由生成器产出。
共享的 OpenXML 管线（styles / 段落 / 表格 / 页脚 / 图片 / 图表 / JSON 解析）只在 `generate.mjs` 里写一次，
场景之间只差一组排版常量：

```bash
node tools/docx-skills/generate.mjs
```

改共享内核 → 重新生成 → 三个技能同时获得修复，不会出现「改了公文忘了通知」的漂移。

### ⚠️ 改完记得同步到内置副本

平台内置版是 `out/` 的一份**拷贝**（作为嵌入资源分发）。改了生成器后必须同步，否则
「界面上的技能」与「新部署自带的技能」会不一致：

```bash
node tools/docx-skills/generate.mjs
node tools/docx-skills/sync-builtin.mjs   # 把生成物同步到内置副本（嵌入资源）
```

`sync-builtin.mjs` 会对比并只拷贝有变化的文件，同时统一 LF。
（内置目录下文件名须为 `*.skill.txt`：MSBuild 会把 `*.cs.txt` 里的 `cs` 当成文化区后缀，
嵌入名被改写导致运行时找不到；脚本已代你处理命名。）

## 依赖说明

### 运行时依赖：系统字体（容易漏！）

图表与文本渲染依赖**系统字体**。官方 `dotnet:aspnet` 运行镜像**不含任何字体**，
所以 Dockerfile 必须装：

```dockerfile
fonts-dejavu-core   # 基础拉丁字形
fonts-noto-cjk      # 中文（图表中文标签必需）
```

**不装会怎样**：图表报 `图表需要至少一种系统字体，但当前环境未发现可用字体`。
（本机直接跑通常不会碰到 —— Windows/macOS 自带字体，只有精简容器会中招。）

### ⚠️ 装了字体还不够：必须挑到“含中文字形”的那一款

只有 `fonts-dejavu-core`（或任何一个纯拉丁字体）时，图表**不会报错**，而是把中文全部画成
**空心方框（notdef）**——用户看到的就是“中文乱码/一串方框”，而英文坐标数字正常，极易误判为渲染错乱。

实测踩到：图表字体原先只按“族名命中候选名单”就选定，容器里前几位候选
（Microsoft YaHei / SimHei / SimSun / Arial）都不存在，第一个命中的是 `DejaVu Sans`（**纯拉丁**），
于是中文标题 / 分类标签 / 系列名全变空框。

现已在共享内核里改成：命中候选后还要用 `Font.TryGetGlyphs` 逐个验常用汉字，
只采用**真的含中文字形**的字体；名单里也补上了 Linux/macOS 的常见中文字体族名
（`Noto Sans CJK SC` / `Source Han Sans SC` / `WenQuanYi Micro Hei` / `Droid Sans Fallback` / `PingFang SC` 等）。
容器里现在会正确选到 `Noto Sans CJK SC`。生成的文档会返回 `chartFont` / `chartFontCjk` 两个字段便于排障。

（注意：`fonts-noto-cjk` 是 CFF/OTTO 字体。它对图表渲染没问题，问题只在“有没有被选中”。
修改字体名单时请保留字形验证，否则在服务器上会静默回退到拉丁字体。）

### ⚠️ 另一个坑：标点被画成竖排（`SixLabors.Fonts` 必须钉 1.0.1）

图表里的破折号 `—` `–` 被画成**竖线**，`（）「」『』【】《》` 被**旋转 90°**，而汉字与
`、。：；！？` 正常——看起来像“部分符号方向错了”。

根因**不在字体**：同一份字体（wqy-microhei.ttc）用 FreeType/PIL 渲染是横排正确的，
容器里 7 种中文字体（Noto Sans/Serif CJK、WQY Micro Hei/Zen Hei、AR PL UMing/UKai、
Droid Sans Fallback）在 ImageSharp 下**全部**如此，所以是库的 shaping 问题：
**`SixLabors.Fonts` 1.0.0 错误地对 CJK 字体套用了竖排（`vert`）字形替换。**

而 ImageSharp 2.1.5 对 `SixLabors.Fonts` 的依赖是 `>= 1.0.0`，平台的 NuGet 解析器取
**最低满足版**，于是默认落到 1.0.0。**显式声明 `#r "nuget: SixLabors.Fonts, 1.0.1"` 即修复**
（1.0.1 仍为 Apache-2.0，不受 Six Labors 从 2.0 起的 Split License 影响）。

该声明写在 `tools/docx-skills/generate.mjs` 的共享 banner 里，会带进三份场景技能；
**不要当成“多余引用”删掉**（单测 `ChartSkill_PinsSixLaborsFontsAtLeast101` 会拦住）。

### ⚠️ 坑：饼图扇区必须自己围「圆心 → 弧 → 圆心」

`PathBuilder.AddArc` **只是往当前图形里追加一段弧**：它既不先移到圆心，也不会自动补上两条半径。
只写 `AddArc`（哪怕再加 `CloseFigure`）得到的是「弧 + 弦」围成的**弓形**，面积远小于扇形——
4 项饼图约 14%、40 项时只剩 0.8% 的彩色像素，看着就像整张图没画。
正确做法是显式 `MoveTo(圆心)` → 沿弧 `LineTo` 走一圈 → `CloseFigure()`；
本仓库用每 2° 一段的多边形逼近（弦高远小于 1px，肉眼不可见）。

> 别改回 `AddArc` 单用：`ChartOverflowTests.Docx_PieChart_DrawsFilledDisk` 会因实心度不足而失败。

### 技能依赖：NuGet 包

技能声明三个 NuGet 包（钉住相容版本）：

```
#r "nuget: DocumentFormat.OpenXml, 3.2.0"
#r "nuget: SixLabors.ImageSharp, 2.1.5"
#r "nuget: SixLabors.ImageSharp.Drawing, 1.0.0"
```

- **ImageSharp 实测可用**（纯托管，无原生依赖）—— 这是图表能力的基础。
- **必须显式钉住 ImageSharp 2.1.5**：`Drawing 1.0.0` 依赖它；若不写，解析器会同时拉入 2.1.7 与 2.1.5 两份引用。
- **SkiaSharp 不可用**：它依赖原生二进制，而平台的引用解析器只解析托管程序集。
- 图表库与 OpenXML 有同名类型（`Color` / `PointF` 等），生成的代码已用 `using` 别名（`ImgColor` / `ImgPointF` / `ImgRect` / `ImgEllipse`）避开二义性，**改代码时勿删别名**。

## 平台约束（写这类技能必读）

1. **预置 using 不含 `System.IO`** —— 平台 Preamble 只给 `System`/`Linq`/`Text.Json`/`Net.Http` 等。
   用到 `Path`/`Directory`/`File` 必须自己写 `using System.IO;`，否则 `CS0103`。
   （生成的技能已包含，勿删。）

2. **`#r "nuget: 包, 版本"` 的版本号是提示，不是锁** —— 实测写 `3.2.0` 会还原到 `3.5.x`。

3. **入口必须是 `public static string Run(string input)`**（同步，不接受 `Task<string>`）。

4. **执行上限与 12,000 字符输出上限** —— 自建技能 **10 秒**，**内置技能 60 秒**
   （`Agents:DotnetSkillTimeoutMs` / `Agents:BuiltinSkillTimeoutMs`，见 `AgentOptions`）；
   生成长文档时注意；技能只返回文件路径与摘要，不要把正文回灌给模型。

5. **`dotnet` 技能仅管理员可建，且一律强制人工审批**（平台安全策略）。

## 已知边界

这几个技能是**结构化排版**能力，不是排版引擎：

- ❌ 不支持套用用户上传的现成模板（平台技能无法携带/读取模板资产）
- ❌ 不支持 XSD 校验闸（无后置校验钩子）
- ✅ 目录 / 图片 / 图表已支持；TOC 需在 Word 里更新一次域（正常行为）
- ✅ 产物直接落为附件，可在聊天区点击下载
- ⚠️ 若模型在调用时自作主张传了 `outputPath`（不由 `AGUI_DOCX_OUT` 接管），文件会落在该路径：
  虽仍能下载（标记里的路径就是实际路径），但该目录若是容器内非挂载路径，重建后即丢。
  提示词里最好明确「不要传 outputPath」，让技能落在卷内的默认目录。

如需模板套用与校验闸，需要平台先支持「技能携带伴生资产文件」，属平台改造。

## 维护提醒

加入目录/图片/图表后源码增至 ~44KB（编译耗时上升，但**超时只计 `Run` 执行、不含还原与编译**，实测仍远低于 10s）。
若继续叠加特性（如原生可交互图表、多节页眉页脚），请重新评估是否撞到 10s 超时，或再拆技能。
